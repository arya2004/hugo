# Verified compatibility and trust notes

**Current override:** [PRODUCT_CHANGES.md](PRODUCT_CHANGES.md) records the newer user-requested private repository project model. The application treasury is now intentionally adapted for one project and admin-only funding; earlier statements of byte-for-byte app-contract equivalence and community funding describe the pre-revision implementation only. Root sources and supplied migrations remain unchanged. Earlier test logs do not validate the revised contract.

The blueprint outside `app/` has not been edited. The two supplied SQL files and the treasury contract are copied byte-for-byte; `cmp ../sql/001_initial.sql supabase/migrations/001_initial.sql`, the equivalent 002 comparison, and contract comparison all succeeded.

- Migration 002 allows five job attempts and immediately clears failure leases, while the API specification requires three attempts and bounded backoff. Migration 004 wraps the supplied functions with a three-attempt guard, exponential backoff and attempt fencing; it does not replace the supplied SQL. Application workers call only the wrappers. The original RPCs remain service-role only. Do not call them directly from another worker.
- Supplied merge status CHECK permits VERIFIED, QUEUED, EVALUATING, EVALUATED, FAILED, REJECTED. RECEIVED is an ephemeral HTTP state before GitHub verification; failed retryable work is stored as FAILED with attempts/backoff rather than inventing an unsupported enum. OPEN → CALCULATED is atomic during preview; RESERVING is persisted only while confirming an owner transaction, with errors returning it to APPROVED. No claimable transition precedes a confirmed receipt.
- A prepared program UUID is required before Arc creation to derive its deterministic bytes32 ID. `POST /api/programs` therefore additionally accepts `id`. The browser retains its public UUID/tx/address draft locally for retries; no secret goes in localStorage. The server checks the derived chain ID against ProgramCreated and the separate configured voucher signer.
- PostgREST can serialize numeric as JSON numbers. The additive `*_safe` views return all monetary and block-number columns as text and use `security_invoker=true`. Server reads use those views. All underlying tables have RLS, with no browser policies.
- Current Arkiv SDK 1.0.1 uses `defineSchema`, typed columns and `.select().from(schema).ownedBy(issuer)` as shown in the live first-entity documentation. The app uses those verified types rather than the blueprint's older untyped entity-query sketch. Programs live 30 days; contributions 90 days, with a durable renewal queue. A recovered existing entity has no fabricated tx hash: the publication record leaves it null.
- Official CRE CLI v1.39.0 uses `cre version`. `cre init` requires authentication even for noninteractive scaffolding. It failed with “not logged in and no CRE_API_KEY set”. Official public templates at commit `d0223f31182c76bc36b1cc9d47b13b18efcf2bf6` were inspected instead; do not describe this project as successfully generated by `cre init`. TypeScript 6.0.3 breaks the CRE SDK compiler (`ScriptTarget.ESNext` undefined), so its separate toolchain pins the official template's TypeScript 5.9.3. Exporting parameterized handler functions also prevented WASM compilation; only the zero-argument entry point is exported. Real WASM compilation now passes. Simulation remains blocked, with actual failure transcript retained.
- Root development tooling uses Hardhat 3's in-process EVM and ephemeral random accounts. Ganache was removed after its bundled dependency advisories. The application runtime audit is clean; development/compiler advisories remain in `evidence/audit-development.json` and `../cre/evidence/audit.json`. CRE SDK 1.23.0 and Hardhat still depend on Zod 3, which has an oversized collection advisory. Public app body/evidence sizes are capped; CRE report size is capped at 64 KiB. Do not force-install an incompatible Zod major inside these SDKs. These local toolchain advisories are not represented as fixed.
- A compiled contract tested locally does not establish Arc USDC transfer compatibility. A live read verified chain ID and `decimals()==6`; approvals, transferFrom, deployment, funding, reserve and claims still need funded testnet wallets.
- The treasury signer is trusted within every reserved epoch. It does not enforce per-recipient approved shares onchain. A compromised signer can redirect reserved funds; owner rotation invalidates old outstanding signatures. This prototype is testnet-only. Inbox authentication does not make public chain payouts confidential.
- Free hosting does not supply 0G inference credits, faucets, accounts or automated CRE settlement. This is a simulated read/validation workflow, with no onchain CRE receiver.
