# Private, source-control-independent redemption

The selected flow is a private invitation link plus an email verification code, followed by a signed receiving-wallet challenge. The contributor never creates an application account or signs in to GitHub to redeem. There is no contributor profile, search directory or reward history UI.

The repo admin confirms the email address privately with the MR creator, then sends the claim invitation from the private MR reward row. The application does not assume that a commit email is genuine or that a public source-control API can reveal someone else's verified private email. This is an explicit trusted-maintainer delivery attestation, not an automatically verified source-control email lookup. A future provider adapter can replace this contact attestation; redemption itself is independent of GitHub, GitLab or any other forge. Current merge ingestion/evaluation and repo admin onboarding still support GitHub only; full GitLab support is not claimed.

Invitations contain a random 256-bit token in the URL fragment. The browser removes it from its URL on load, and exchanges it only through same-origin POST bodies. Link previews/GET requests do not consume claims. The database stores only a token hash. The recipient email is AES-256-GCM encrypted using server-only CLAIM_DELIVERY_KEY. Opening the link sends a six-digit code only to that stored contact, with a ten-minute expiry, five-attempt maximum and resend cooldown. Codes are HMACed with the server secret. Successful verification atomically consumes the note and clears its email and token; it creates a short-lived, HttpOnly, same-origin session scoped to exactly one reward.

The private session can bind a wallet through a one-use, domain/chain/session-bound signed challenge. The first voucher permanently locks its recipient. The existing contract enforces one reward and one successful claim per merge. On confirmed payout, the claim session, challenges and invitation are deleted. Expired private delivery data is cleaned on the next claim start. Minimal MR/payment/replay proof stays; existing raw assessment data is minimized under migration 010. This is data minimization, not a promise of zero server/provider logs or blockchain anonymity. The email provider handles delivery metadata, and the Arc payment address/amount are public.

Apply migrations 001–011. Set CLAIM_DELIVERY_KEY (32 random bytes encoded as 64 hex characters), RESEND_API_KEY and CLAIM_EMAIL_FROM with a verified sender domain in Vercel/server configuration. The server uses the official Resend send-email API. No real email was sent during implementation; no real delivery receipt is claimed. Credential-free UI preview shows an explicitly labelled sample code 123456 at /redeem.

Alternative: a random claim-secret handed over in a private channel can avoid email entirely. That is a bearer capability: anyone who obtains it can redeem. Fresh receiving wallets reduce reuse, but neither approach hides public USDC transfers. Shielded settlement would be a separate product/contract integration and is not implemented here.

Primary references: https://docs.github.com/en/rest/users/emails (verified-email lookup is for the authenticated user), https://docs.gitlab.com/api/users/ (provider-specific user/email permissions), https://resend.com/docs/api-reference/emails/send-email (actual delivery endpoint).

The former publication workflow now performs hourly authenticated cleanup of expired private delivery/session data instead of publishing records. This requires the central workflow to be installed on the repository default branch and its app URL/worker secret configured. It has not run in this workspace; until installed, cleanup occurs when a claim is opened.
